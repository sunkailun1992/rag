# 项目版本变更规范

本规范用于 AI 判断是否需要修改版本号、怎么修改版本号，以及公共包消费者如何同步。若用户在当前任务中明确指定版本号，以用户指定为准，并在交付说明里解释原因。

## 基础坐标

Java / Spring / Gradle 新项目默认使用以下基础坐标：

```groovy
group = 'com'
version = '1.0.0'
```

- 已经发布过的项目保持现有 `group` 坐标，不因为补文档或小版本升级强行迁移；修改 `group` 属于发布坐标迁移，必须单独评估 Maven 仓库、消费者依赖和回滚方案。
- 非 Java 项目没有 Gradle `group`；如果存在 `package.json` 或其它制品版本，递增规则仍按本规范执行。
- 构建制品 `version` 不等同于接口版本、Nacos dataId 版本、流量治理头 `X-Release-Version`、数据库乐观锁 `version` 字段。

## 什么时候改 version

- 修改生产代码、运行时配置、构建脚本、数据库脚本、公共示例，或会改变制品行为的依赖版本时，本批未提交改动只提升一次 `version`。
- 纯 README、AI 编程规范、注释说明、非运行时文档改动，不强制提升制品 `version`。
- 只修改 Nacos 远程配置且没有提交仓库文件时，不修改仓库构建版本，但交付说明必须写清 dataId、group、namespace 和验证结果。
- 同一批改动后续补测试、补文档、修格式，不重复提升版本。

## 怎么改 version

项目采用三段式 `MAJOR.MINOR.PATCH` 顺序编号；MAJOR 为无多余前导零的非负整数，MINOR/PATCH 各为单个 0–9 数字。

1. PATCH 小于 9 时只加一，例如 `1.2.8 -> 1.2.9`；PATCH 为 9 时 MINOR 加一、PATCH 清零，例如 `1.2.9 -> 1.3.0`；两者都是 9 时 MAJOR 加一、其余清零，例如 `1.9.9 -> 2.0.0`。
2. 不生成 `1.2.10`、`1.10.0`，不跳过未占用的正常版本，不为编号创建空发布。同一批未提交改动只提升一次；纯文档/规则不提升业务制品。
3. 修改前 fetch，核对构建文件、远端 main、在途分支、tag 和私库已用版本；使用未占用且高于已使用版本的新版本，不只看落后本地分支。
4. 旧违规编号只向前修正并记录映射，不降级、不重写历史。例如没有更高占用时 `1.3.105 -> 1.4.0`、`1.10.0 -> 2.0.0`；历史 tag 与不可变制品保持原样。
5. 功能、兼容修复和破坏性改动均按同一进位顺序。破坏性变更另外说明接口、数据库、配置、RPC 或坐标迁移与回滚，不能用编号规则代替兼容评估。
6. 项目版本、第三方依赖、公共库精确版本、Prompt 与 AgentCard 等资产分别管理，不机械替换所有数字。提交前说明原/新版本、占用核对、进位依据和验证；已有版本校验不得删除或放宽，未接入时人工核对。

## 公共包和消费者

- 本 GitHub 个人项目的公共工具包使用 `com:utils`，公司项目使用 `com.kellen:utils`；两者共用同一私有 Maven 地址，以 group 隔离制品。Java 包名 `com.kellen.*` 与 Maven group 分开管理，不随制品坐标迁移。
- `utils` 等公共包改动后，先提升公共包版本并发布到 Maven Local 验证。
- 消费者只引用已经存在的精确版本，不使用动态版本、版本范围或未发布的版本。
- 消费者升级公共包后，必须至少执行编译验证；涉及认证、租户、多数据源、Seata、Dubbo、网关头、序列化或数据库行为时补充测试。
- 从 `main` 分支提交并推送公共包时，必须同步发布远程私有 Maven 制品；消费者仓库再更新依赖版本并验证。

## 交付检查

- 最终说明写明旧版本、新版本、升级原因、是否发布 Maven、消费者是否同步、执行过哪些测试。
- docs-only 任务要明确说明未提升制品版本的原因。

本轮个人业务库从 MySQL 迁移为 PostgreSQL，连接键和方言不兼容，服务版本按 MINOR 顺延为 `1.2.0`；公共依赖固定为 `com:utils:1.6.0`。历史已发布版本不覆盖；是否部署以目标环境验收为准。
